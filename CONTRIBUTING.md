# Contributing

**superpowersplus does not take outside contributions.** There is no pull
request process here — Superpowers' issue and PR templates were removed rather
than rewritten, because there is no workflow for them to serve. What follows is
how to report something, and how to work on the code if you are running your
own copy.

## Reporting a problem

Open an issue on
[this repository](https://github.com/rodrigopaitach/superpowersplus/issues).
That is the single channel: bugs, a skill that behaves wrongly, anything
covered by [`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md), and anything that is not
a security vulnerability. Vulnerabilities have their own path in
[`SECURITY.md`](SECURITY.md).

A report is more useful with the version (`/plugin` list, or the `version` field
in `.claude-plugin/plugin.json`), the harness you are on, and what you expected
against what happened. Do not paste credentials, tokens, or real personal data —
[`CLAUDE.md`](CLAUDE.md) forbids them in the repository and an issue is part of
the repository.

## Contributing to Superpowers itself

Improvements to the original skills and workflow belong at
[obra/superpowers](https://github.com/obra/superpowers), under its own
guidelines and templates. **Nothing sent here reaches them.** superpowersplus is
a derivative work with no connection to their maintainers, their review process,
or their release schedule, and a change landed here never propagates upstream.

## Development setup

Zero third-party dependencies for the plugin itself. Only the
`brainstorm-server` test suite needs `npm`.

```bash
git clone https://github.com/rodrigopaitach/superpowersplus.git
cd superpowersplus

# Activate the versioned hooks. Not automatic: .git/ is not versionable, so
# every clone opts in. Without this, the pre-commit gates never run for you.
git config core.hooksPath githooks

# Only for the brainstorm-server suite.
npm install --prefix tests/brainstorm-server
```

## Running the tests

CI runs every static suite on every push; the list and what stays out on
purpose are in [`CLAUDE.md`](CLAUDE.md).

```bash
# The Node suite.
npm test --prefix tests/brainstorm-server

# The shell suites — each directory owns its entry point.
bash tests/shell-lint/test-lint-shell.sh
tests/hooks/test-session-start.sh
tests/hooks/test-check-changelog.sh
tests/hooks/test-check-links.sh
tests/hooks/test-check-skill-size.sh
tests/codex-plugin-sync/test-sync-to-codex-plugin.sh
tests/antigravity/run-tests.sh
tests/codex/test-marketplace-manifest.sh
tests/codex/test-package-codex-plugin.sh
tests/systematic-debugging/test-find-polluter.sh
tests/kimi/run-tests.sh
tests/opencode/run-tests.sh
node tests/pi/test-pi-extension.mjs
```

**Run `tests/codex/test-package-codex-plugin.sh` only on a clean tree.** It
packages from a git ref and compares against your working tree; with anything
uncommitted the two disagree and it fails with no defect present. The mechanism
is documented in [`CLAUDE.md`](CLAUDE.md).

The suites that dispatch a live agent — `tests/claude-code/`,
`tests/explicit-skill-requests/`, `tests/skill-behavior/` — are not part of this
list. They cost tokens and are non-deterministic; running one is a deliberate
decision, and `tests/skill-behavior/README.md` states the policy.

## Release discipline

Not duplicated here, because a second copy is a copy that goes stale. The rules
live in [`CLAUDE.md`](CLAUDE.md) and are enforced, not merely stated:

| Topic | Where |
|---|---|
| Semver, and what counts as PATCH / MINOR / MAJOR | `## Versioning` |
| `[Unreleased]` does not survive more than one cycle of work | `## Versioning` |
| Version bumps go through `scripts/bump-version.sh`, never by hand | `## Versioning` |
| Release bodies are generated by `scripts/release-notes.sh`, never assembled | `## Versioning` |
| `--repo` on every `gh` invocation, reads included | ``## Running `gh` `` |
| Content changes carry their `CHANGELOG.md` entry | `## Preparing a commit` |
| Preparation and `git commit` are never chained in one `&&` | `## Preparing a commit` |

**The changelog row is enforced** by `scripts/check-changelog.sh`, in the
pre-commit hook and again by CI over the pushed range, so a clone that skipped
`core.hooksPath` still gets caught. **The chaining row is not, and cannot be**
— no script can see that an edit and a `git commit` were two separate
decisions rather than one `&&`. It is a rule you follow, and the reason it is
written down is that it was broken once and the failure was invisible: a
`CHANGELOG.md` edit failed on a wrong anchor, the commit and the push ran
anyway.

**Five gates run locally** — `check-docs-sync.sh`, `check-frozen-history.sh`,
`check-changelog.sh`, `check-links.sh` and `check-skill-size.sh`, all wired
into `githooks/pre-commit`. **CI runs those five plus
`check-skill-behavior-records.sh` and `lint-shell.sh`** over the pushed range.
The records check has no local counterpart, and since it gained its staleness
pass that is a deliberate cost rather than a free one: it now fails on any edit
to a rule under `skills/` that a `RESULT-*` measures, which is the point of it.
It stays out of the hook because it reads git history, and the hook runs before
the commit that history would have to contain.
